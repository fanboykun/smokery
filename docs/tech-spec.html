Design constraints
Compiler-first
UI → canonical config → compiler → plan. Runner executes plan only.
Explicit over magic
System suggests; user always overrides classification, shapes, destructive flags.
Persistent + collaborative
Run results are first-class artifacts with comments, history, and sharing.

Process map
api-server (Go)
  • REST API on :8080
  • WebSocket /ws/runs/:id
  • Serves compiled plans
  • Stores + queries results

  • Polls River job queue
  • Fetches plan from API
  • Executes HTTP calls
  • Streams progress via WebSocket
  • POSTs structured result back
  • Can run as standalone CLI

Real-time Architecture
Live run progress from runner → browser
Event flow
Runner goroutine
  → emits RunEvent to channel

API WebSocket handler
  → reads channel
  → writes JSON frames to client

SvelteKit page
  → wraps native WebSocket
  → feeds Svelte writable store
  → reactive UI updates per event
Svelte store pattern
// src/lib/stores/runEvents.ts
export function createRunStore(runId: string) {
  const { subscribe, update } = writable<RunState>(initial)
  const ws = new WebSocket(`/ws/runs/${runId}`)
  ws.onmessage = (e) => {
    const event: RunEvent = JSON.parse(e.data)
    update(s => applyEvent(s, event))
  }
  return { subscribe, close: () => ws.close() }
}
Phase 2 — Redis pub/sub

For horizontal scaling: replace direct channel with Redis pub/sub. Runner publishes to runs:{id}:events. Each API pod subscribes and fans out to connected WebSocket clients. No frontend code changes required.
